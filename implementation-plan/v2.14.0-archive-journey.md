# v2.14.0 — Quiz Archive and Journey improvements

Implemented from main after merged PR #27, on `codex/v2.14.0-archive-journey`. Release tracking: [#32](https://github.com/okrable/pundit-app/issues/32). Native layout acceptance is related to [#29](https://github.com/okrable/pundit-app/issues/29), not a claim to close its broader scope.

## Product and boundaries

Archive is an independent Games entry, also available after today's quiz. The catalogue lists validated past five-question quizzes newest first, twenty at a time. It excludes today/future dates using the London quiz day. Selecting a date opens the established QuestionCard, typewriter reveal and scoring. The timer starts only when options are visible; correct answers at zero still earn ten points. Archive gameplay and sharing identify the mode explicitly.

One local active attempt and one latest summary per played date are stored under the originating identity. Summaries retain date, content version, score and five correctness flags, without selected-answer/timing history. The active attempt temporarily retains the content, locked selections and deadlines needed to resume. A deliberate replay replaces that date's latest summary on completion. Guest archive history is never adopted into an account. Logout/account changes hide the previous identity's records immediately.

A cached unfinished quiz can continue after a network failure. Uncached content requires connectivity. An authoritative unavailable response is not treated as an offline cache hit. Changed content invalidates an incompatible active attempt and explains the restart. Browsing has loading, empty, retry and end-of-catalogue states; there is no promise of unlimited fresh content.

`canAccessArchive` is the shared access decision, enforced by both archive endpoints. It currently grants guest and authenticated access. No billing, quotas, entitlements or placeholder paywall exists. A paid release must separately decide cached-content access, restoration and treatment of existing players. The UI makes no permanent-access promise.

Journey remains daily-only. Search starts after two normalized characters, debounces for 250 ms and returns at most eight canonical names. Its server catalogue cache lasts fifteen minutes. All indexed players, including retired players and today's answer, follow the same ranking rules. Source alternate names are not automatically approved aliases: the reviewed alias map is explicit and currently empty. Birth year and position distinguish names where available. Selecting a suggestion fills the input; Tab/Enter and touch selection do not submit. Stale responses are discarded; failure never disables free-text/surname matching.

Give Up requires confirmation and reveals the footballer. Both terminal outcomes use distinct recap/share copy without including the answer in shared text. Given up is never a successful solve. An authenticated local result is provisional until server confirmation; outcome plus pending sync are written atomically. Cache writes are serialized by identity, and a delayed older-day response cannot replace today's record. Sync/adoption are bound to the original account/session. Only current London-day pending work is retried. Failed storage does not count as durable completion. Guest adoption first durably binds the pending outcome to the authenticated account, then removes the guest copy.

No Journey practice, hints, currencies, leagues/cups, subscriptions, CMS, bulk migration, TLS changes or unrelated styling refactor is included.

## Result integrity and compatibility

Migration **021** adds nullable `results.answer_details`. New results persist actual submitted selections, timings and correctness in the result transaction. Existing rows remain unchanged. The authenticated submission path reads an existing result before querying answer keys. Duplicate/conflicting insert losers read the winning row. A single serializer returns canonical scores and correctness on every retry, even after a lost response. Missing historical selection, timing and question details are omitted, never reconstructed from a retry. Recaps explicitly tolerate unavailable details. The compact daily-result read contract is unchanged.

User-row transaction locks and Cockroach serialization retries coordinate submission, guest adoption and legacy finalization. Totals, best score and streaks are projections of persisted results, not increments gated by last_played. Achievements are applied only for a newly inserted result; retries return canonical achievement state.

Migration **022** adds `career_game_results.outcome`, defaulting existing records/legacy solve-only inserts to `solved`. The unique user/game constraint and insert-without-overwrite enforce first-persisted-outcome wins. V2 requests send `contractVersion: 2` and an explicit outcome; reads opt into the outcome-aware contract. Legacy requests remain solve-only. Legacy success-only reads withhold given-up records, and a conflicting legacy solve receives 409 rather than a false success. Older clients cannot display the richer given-up recap and may show retry/error UI; upgrade is needed for the new presentation.

SemVer remains **2.14.0**: these are additive features and integrity fixes, with unchanged scoring, auth ownership and supported compact reads. Historical missing fields are represented honestly within the existing answer-object response shape. This classification does not imply that older clients gain the new presentation.

## Content and analytics

BigQuery remains the post-cutover source; Cockroach remains the pre-cutover question source and transactional store. Inspection found 41,268 dictionary players, including 17,809 inactive records. Daily ranks 1–5 are validated independently of optional Journey rank 6. Archive publication follows the existing date/source cutover and successful-generation source rules, then validates complete ranks, prompts, distinct options and correct answers. Generation success is not licensing approval; payload provenance explicitly reports licensing as unknown and retains source question/player identifiers.

`getArchiveCatalog` and `getArchiveQuiz` are read-only. `searchPlayers` accepts POST so search text is not put into URL logs. Archive completion never calls daily submission, guest daily adoption or achievement endpoints. Content versions derive from the stable question signature. The archive catalogue has a five-minute server cache and validates every playable bundle. The read-only adapter check returned 72 eligible dates (27 May–10 August 2026) and 41,268 players; dates without published matching source bundles are not advertised.

Analytics extend the existing opt-out, installation identity and retention controls with fixed event names and allowlisted properties for archive opening/start/completion, Journey start/outcome, autocomplete failure and bounded duration. No guesses, search text or free-form answers are collected. Completion is emitted for a new local terminal transition, not hydration or synchronization retries.

## Preview and migrations

The original deploy-preview DATABASE_URL pointed at production. This release adds a fail-closed preview connection selector: deploy-preview and branch-deploy require a separate `PREVIEW_DATABASE_URL`; they cannot silently fall back to DATABASE_URL. The build embeds a non-secret preview marker because build CONTEXT is not guaranteed in the function runtime ([Netlify environment documentation](https://docs.netlify.com/build/functions/environment-variables/)). Production still uses its existing DATABASE_URL. No TLS/pool configuration was changed apart from waiting for query settlement before release.

On 8 September 2026, isolated database `pundit_preview_v214` was created on the existing Cockroach cluster. Table definitions were copied using LIKE INCLUDING ALL; this is an acceptance schema copy, not a full backup/restore or production-data copy. Only football question content was copied. Production users, results and analytics were not copied. Migrations 021 and 022 were applied to this isolated database only. **Hosted preview blocker:** Netlify returned `JSONHTTPError: Forbidden` when creating `PREVIEW_DATABASE_URL`; API readback confirmed the key is absent. A Netlify administrator must set this secret for **deploy-preview / functions** to the isolated database and rebuild the preview. The existing production DATABASE_URL must remain unchanged. Branch-deploy also remains closed until it receives its own explicit preview setting. The isolated database tests used the connection directly, not a deployed preview.

Before any production release, apply additive migrations 021 and 022 in order under the normal release process. They are idempotent. Deploy the outcome-aware backend with its conflict protections before enabling updated clients. Leave this PR unmerged until preview/device acceptance is approved. No production migration or release is part of this task.

Rollback may disable Archive/autocomplete/Give Up entry points, but retain both columns, stored results and terminal-conflict protections. Do not restore a backend that treats given-up records as successful solves. Do not drop result data or reconstruct missing historical details.
